Three things about this table are unusual enough to state rather than leave for a reader to notice.

**The validation window is reused from Generation 1.** It is the same 36 months Generation 1 read at
its own Gate 4. §2 below is the full disclosure of what that costs.

**There is a 24-month gap between the windows.** 2024-08-01 → 2026-07-31 was Generation 1's final
holdout. Generation 2 assigns it to no window and will never read it, in any stage, for any purpose.
It was read exactly once, under Generation 1's holdout authority, and that authority is spent. It is
not available as extra validation data, not as a warm-up buffer, and not as a sanity check. Leaving
it unassigned rather than folding it into a Generation 2 window is deliberate: an unassigned window
cannot be quietly reclassified later.

**The Generation 2 holdout has not elapsed.** Today is 2026-08-15. The window runs to 2028-07-31, so
23 of its 24 months are still in the future. It cannot be read now because it does not yet exist; it
may not be read when it does exist until the constitutional holdout gate, and it may not be
shortened to whatever happens to be available at that time. See §3 for the five sessions of it that

## 2. Disclosed limitation — validation-window reuse

The following text is mandated by the Generation 2 operating instruction and is reproduced without
alteration. It must appear, unchanged, in every later Generation 2 report that references the
validation window.

> Generation 2's validation window (2021-08-01 → 2024-07-31) overlaps the exact period Generation 1
> used for its own Gate 4 validation read. The researcher therefore already knows, from Generation
> 1's published report, approximately how SPY (and by extension the broad market) behaved in this
> window — including its Sharpe ratio (≈0.20), total return (≈2.15%), and fold-by-fold sign pattern
> (7 of 12 positive). Generation 2 tests a different hypothesis (cross-sectional multi-asset
> selection vs. single-symbol mean reversion) over the same calendar period, which limits but does
> not eliminate the concern. This is a real multiplicity cost, disclosed and not minimized, and it
> is the reason Generation 2's validation result alone — without a clean holdout confirmation —
> cannot be treated as sufficient evidence of an edge.

The three figures the text attributes to Generation 1's published report are quoted from disk rather
than from memory, and the exact fields are recorded here so a reader can check them:

| Sharpe ≈0.20 | `0.2025294206503088680547420121230750` | `run_evidence.base.sharpe` |
| Total return ≈2.15% | `0.0215` | `run_evidence.base.total_return` |
| 7 of 12 folds positive | `positive_fold_count` 7, `completed_fold_count` 12 | `gate_conditions.S4-C6.evidence.condition_evidence` |
| "SPY … by extension the broad market" | `['SPY']`, contribution `{'SPY': '2.15'}` | `run_evidence.runs[0].measure.symbols_loaded`, `.contribution_by_symbol` |

Two further remarks, which extend the disclosure rather than soften it:

- The knowledge is not confined to Generation 1's report. The 2021-08 → 2024-07 period is public
  market history that any researcher alive in 2026 has lived through. Generation 1's report makes a
  specific part of it precise, but the broad shape of the window was already known. A pre-registered
  cross-sectional rule limits how that knowledge can be exploited; it does not make the researcher
  ignorant.
- The disclosure is a reason to weight the eventual holdout result more heavily, not a reason to
  discount a Generation 2 validation failure. A failure on a window whose character is already known
  is if anything stronger evidence against the hypothesis than a failure on an unseen window.

## 3. What is on disk today, and the five-session problem

The acquired dataset under `data/normalized/daily/` currently runs to **2026-08-07** for all 34
universe members. That is past the start of the Generation 2 holdout window. Five sessions —
**2026-08-03, 2026-08-04, 2026-08-05, 2026-08-06, 2026-08-07** — lie inside a window this document
seals.

This is stated plainly because a sealed window with rows already sitting on disk is exactly the
condition under which a leak happens by accident rather than by intent. What is done about it:

1. The five sessions are **not deleted**. Deleting acquired data to make a guard easier would
   destroy reproducibility of the Generation 1 record, whose manifests cover these files.
2. No Generation 2 code reads them. Enforcement is §4 below: a hard window bound applied in code,
   not a convention.
3. They are not, and will not be, part of the eventual Generation 2 holdout read. That read requires
   the full 24 months, re-acquired after 2028-07-31, and cannot be assembled from a partial prefix.
4. Should the dataset be re-acquired between now and then, more of the sealed window will appear on
   disk. The rule does not change and the guard does not need updating: everything at or after
   2026-08-01 is unreadable until the holdout gate, regardless of how much of it exists.

The same reasoning applies with greater force to the Generation 1 holdout, 2024-08-01 → 2026-07-31,
all 24 months of which are on disk right now.

## 4. Enforcement

The bounds are enforced in code by the existing `ResearchWindow` mechanism, not by convention.
`ResearchWindow.check()` raises `WindowViolation` for any session outside its bounds, and
`MarketView._check` raises `LookAheadError` for any session after the view's `as_of` date. Every
Generation 2 backtest is constructed with the development window, so a read of 2021-08-01 or later
is a raised exception rather than a silently wrong number.

Generation 2 adds one guard of its own, `stockedge100.strategies.g2_window_guard`, which:

- asserts the window handed to any Generation 2 Stage 3 run ends on or before `2021-07-31`;
- asserts that no `PriceSeries` loaded for a Generation 2 Stage 3 run contains a session after
  `2021-07-31`, by inspecting the loaded bars rather than trusting the loader;
- raises on any attempt to construct a Generation 2 research window that intersects either
  prohibited period, `2024-08-01 → 2026-07-31` or `2026-08-01 → 2028-07-31`.

The third clause is deliberately broader than this stage needs. Stage 3 could be protected by the
development bound alone; the prohibition on the two holdout windows is written so that it survives
into stages this document does not authorize.

The guard is covered by tests that fail if it is removed or weakened. Their names and counts are
recorded in the Stage 3 (Generation 2) test summary.

## 5. Binding rules

1. The Generation 2 holdout window is read exactly once, at the constitutional holdout gate, after
   2028-07-31 has passed in real calendar time, and never before — not in part, not as a preview,
   not to check data availability.
2. Generation 1's holdout window, 2024-08-01 → 2026-07-31, is never read again by anyone, for any
   purpose, in any generation.
3. No parameter, threshold, symbol, weight, or rule may be chosen using any value inside the
   validation window or either holdout window.
4. These boundaries may not be recomputed, widened, narrowed, or shifted by any later stage. If the
   dataset is re-acquired and its coverage moves, this lock still governs.
5. The Generation 2 holdout may not be shortened. A holdout gate reached with less than the full 24
   months available is a blocked gate, not a shortened one.
6. Stage 4 validation for Generation 2 requires a separate, explicitly authorized session. This lock
   does not authorize it, and no result produced under this lock authorizes it.
7. The §2 disclosure text is reproduced verbatim wherever the validation window is referenced. It
   may be quoted at greater length; it may not be shortened, paraphrased, or summarised.
